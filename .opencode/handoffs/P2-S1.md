## Spec notes

- **Retention params (sole source):** `conf/base/platform.yml`
  → `governance_params.retention_days: 365`, loaded by
  `load_governance_params()` (Path default
  `conf/base/platform.yml`, CLI flag `--governance-params`).
  No catalog-metadata path is read. Value 365 mirrors the
  existing `conf/base/parameters/platform.yml`
  `governance_params.retention_days` and the config-schema
  default.
- **Erasure channel:** `run_erasure()` delegates to the
  frozen `erase_subject()` (clear-id form). The CLI exposes
  `--erase` / `--erase-subject` as boolean switches only;
  the clear id is read solely from the
  `FORECAST_ERASE_SUBJECT_ID` env var, never argv, never
  logs. Output prints `subject_hash` + counts +
  `actor_hash` only. The module docstring references ADR
  **D-ERASURE-CLI-1** as the gate for production enablement.
- **Secrets (shell/reference only, env-only):** GCP creates
  the secret shell + workload-SA read grant; AWS creates
  the secret shell only (no value-bearing resource
  anywhere); Azure uses a `data` block to reference the
  named vault secret, so no value enters state. All three
  declare `variable "secret_name"` (default
  `forecast-ml-api-secrets`) and output only the shell id.
  Values are filled out-of-band via the cloud CLIs
  (documented in file comments). Helm values keys remain
  C1-owned and untouched; the CronJob consumes no secret.
- **CLI actor:** `FORECAST_ACTOR` / `FORECAST_OPERATOR`
  env, else the `forecast-ml-retention-job` service name;
  always hashed via the sole `subject_hash` leaf.
- **Dry run:** `--dry-run` plans with the pure
  `check_retention` only and deletes nothing (`swept`
  stays 0). `--erase` + `--dry-run` together is a
  validation error (exit 2). Store errors abort the sweep
  after the frozen enforcer appends a partial audit entry;
  the CLI prints a generic error and returns 2.
